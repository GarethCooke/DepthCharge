Every frame takes

A desk-top order-book terminal whose entire correctness argument rests on one claim: the code between the socket and the pixels does not know which of them it is talking to. This document draws that code — the classes that exist today, the calls they actually make, and the places where the design is carrying load it has not yet been asked to bear.

01 The shape of the whole thing

#1 host-buildable #2 one boundary type #8 one writer

DepthCharge is a pipeline with swappable ends. Bytes arrive from a replay file on a desk or a TLS WebSocket on an ESP32-S3; pixels leave to a terminal or to a HUB75 DMA driver. Between those two swaps sits engine/, which is the same translation units in both cases — not a port, not a shared interface, the same code.

That is the bet the whole project makes, and it is enforced rather than asserted: CMake generates one translation unit per engine header that includes only that header, so the moment an ESP-IDF include leaks into engine/ the host build fails, because the host has no such header to find.

What the build actually produces

The CMake targets encode the same separation, which is what makes the claim checkable rather than aspirational. dc_engine is an INTERFACE library — header-only, so nothing can be compiled into it with the wrong flags. dc_engine_anvil is deliberately its own static library because it is the single target that touches nlohmann/json, and therefore the single target that must not reach the microcontroller. Since M3 stage B it has a twin, dc_engine_anvil_streaming, which is the same declaration implemented without a parser library at all — and which pointedly does not link dc_vendor, so the separation is enforced by the linker rather than asserted in a comment.

It reaches into the engine with exactly two lines: -I ../engine/include, and a build_src_filter naming the single translation unit engine/src/anvil/anvil_frame_streaming.cpp. Nothing is copied or vendored, and the firmware names its parser for the same reason every executable above does.

There is one deliberate crossing in the other direction: dc_tests puts firmware/src on its include path to compile test_frame_reassembler.cpp. That is a header — the WebSocket reassembly state machine, written free of ESP-IDF precisely so it can be tested here — and no firmware .cpp is ever compiled on the host. It is the only piece of stage C that is new logic rather than engine code or a thin wrapper over an Espressif call, and a replay trace cannot exercise it, because the capture tool's WebSocket library reassembled the chunks before writing the line.

02 The vocabulary that crosses the boundary

#2 one boundary type #3 integer ticks only #7 allocation-free

FeedEvent is a plain aggregate with no methods and no ownership. Four kinds share one flat layout, and which fields mean anything is a function of kind. That is a tagged union written without a union — deliberately, because a static_assert on trivial copyability is what lets the render hand-off be a memcpy and lets the whole feed path avoid the heap.

Prices are int64_t ticks and quantities are int64_t steps. There is no floating-point number anywhere in the type, and the conversion from the wire's decimal strings happens in parse_scaled, which refuses to round: a price carrying more precision than the declared scale is a reported error, never a quietly truncated level.

The lifetime rule, which the compiler does not enforce

A Snapshot carries 84–126 levels per side across the committed baseline trace — measured, not assumed. Putting them in FeedEvent by value would make the boundary type kilobytes wide; putting them in a container would make it allocate. So the levels stay in the adapter's reusable AnvilFrame and travel as two raw pointers, valid for exactly the duration of the sink call.

03 The adapter, and the seam inside it

#2 venue mess quarantined #3 no float touches a price #7 no virtual call, no allocation

AnvilAdapter owns every Anvil-specific decision so that Book owns none. Three of those decisions are load-bearing and each one is a place a naive implementation would have gone wrong:

  • The wire seq is decoded and then ignored. Anvil's seq is one global counter shared by every ticker and frame type, so a single socket's subsequence runs backwards — 42 times in five minutes, measured at M0. The adapter synthesises its own dense Seq from receive order and keeps the wire value only as a diagnostic counter. It can therefore never emit Gap{SeqGap}, which is safe only because Anvil's book frames are idempotent full replaces.
  • snapshot and book are the same event. Both become FeedEvent::Snapshot. book is not a delta and treating it as one would corrupt the ladder silently.
  • A malformed frame is dropped, not gapped. Anvil republishes the whole book every ~80 ms, so one bad frame self-heals within a refresh; greying the panel for it would be dishonest in the opposite direction. A systematic failure shows up as a stalled ladder plus a non-zero parse_errors count.

One declaration, two definitions, chosen by the linker

The only genuinely environment-specific work in the adapter is turning JSON bytes into fields. That work sits behind a single free-function declaration, and the implementation is selected by which static library a binary links. It is the cheapest possible seam — no virtual call, no template, no runtime branch — and M3 stage B is where it earned its keep: the second definition landed with zero changes to the adapter, the book, the contract types or the goldens.

What the seam does not cover is the conversion arithmetic. Both parsers include anvil_scaling.hpp and call the same price_text_to_ticks, wire_qty_to_steps, aggressor_from_text and kind_from_type. That split is deliberate and it is where invariant #3 is actually defended: a hand-rolled rewrite fails loudly on JSON structure, but a reimplemented price conversion would fail quietly, one tick at a time, and look like a market difference. Each parser's job stops at finding the token's bytes.

A healthy book frame, end to end

04 The book, and why it is barely a book

#3 integer ticks #5 stale is first-class #7 fixed capacity #8 one writer

Anvil publishes a full top-N replace every ~80 ms. Against a venue like that, book maintenance is not a data-structure problem — "adopt the latest snapshot" is the entire engine, plus a ring of recent prints. The tick-indexed dense window that the architecture describes is real work, but it is M4 work, and building it now would mean building it against no delta stream to test it with.

So Book today is two fixed arrays, a ring, and a status flag. What makes it interesting is not the storage; it is the four ways apply() can end, and the fact that one of them is deliberately impossible-in-practice.

Two states, and only one way back

The asymmetry is the design. Four different things drive the book into Stale; exactly one thing brings it out, and that is a fresh Snapshot. A trade print arriving during an outage is still real tape and is still recorded — but it does not clear the flag, because it says nothing about whether the resting levels are still true.

reject_delta() is the interesting one. Anvil never sends a delta, so on the only venue that exists this branch is unreachable. It exists because the alternative — silently ignoring an event kind the book cannot apply — would produce exactly the failure mode the project is built to prevent. It is a tripwire for a future adapter bug, and it costs one enum comparison per event.

05 When it goes wrong

#5 stale is a rendered state #6 replay coverage

Anvil emits no error frame and no gap frame. Absence of data is the only signal there is, which means the disconnect is synthesised by the transport — and the harness has to synthesise it too, or the host replay would be an analogy rather than a preview.

Two rules were available for a capture file with no disconnect marker. "A mid-stream snapshot means we reconnected" was rejected: the gap would be raised in the same breath as the snapshot that clears it, so the book would never actually be stale and the invariant-5 proof would be vacuous. The rule chosen instead is a watchdog, and the number is measured rather than picked — across two five-minute captures the worst healthy inter-frame gap was 640 ms against a ~70 ms median, so 1000 ms sat 1.6× above the worst healthy silence and 4.5× below the observed drop.

That derivation has since been re-measured rather than re-derived, and it held. M3 stage C put the firmware on a bench and the panel greyed every 15–20 s on a socket that never dropped, with the board reading ~6 messages/s against M0's 15.5 — which reads exactly like a server that has slowed until healthy silence outgrew the threshold. It is not. A fresh twenty-minute capture (20,418 frames) has Anvil faster and steadier than at M0 — 17.02 frames/s, worst gap 391 ms — so re-deriving from current cadence would have moved the threshold down, to ~626 ms, and made the false greys worse. 1000 ms now stands 2.6× above the worst gap in twenty minutes and 5.3× above p99.9, on three times M1's sample.

The board's low message rate is real, and it is backpressure rather than cadence: Anvil sheds to a slow consumer, and sheds evenly. A client deliberately throttled to a quarter of the server's rate receives 4× fewer messages and is still never silent longer than one drain interval, because book frames are coalesced per socket — a backed-up socket gets the newest book on the next tick it can accept, not a queue of stale ones. Throttle a desk socket to the board's own 8.30 msg/s and measure it under the board's own book-event rule and the worst silence is 594 ms, with zero watchdog trips in four minutes; the board shows 2,461 ms. So the multi-second holes are board-side and the watchdog is reporting them honestly. Raising the threshold would have hidden a real 1–2.5 s freeze of the feed pipeline — the frozen-ladder-reading-Live outcome invariant #5 exists to forbid. The constant did not move; the measurement became a golden so that a real future cadence change goes red on the desk instead of grey on the panel (ARCHITECTURE §9, 2026-08-09; harness/replay/NOTES.md M3 addendum).

The detail that makes the stale window real is the timestamp. The gap is dated at prev_rx + 1000 ms — the moment the watchdog would have fired — not at the moment the next frame eventually arrived. In the committed reconnect trace that turns an instantaneous blip between two frames into 3.47 s of grey.

The firmware watches something slightly different, on purpose

M3 stage C implements the same 1000 ms rule on the board — and then arms it from a different event, which is the one place the two halves of this project deliberately disagree. The host driver fires on a hole in rx_ns between any two frames, which is exact for a trace file: in a capture every frame parses, so "a frame arrived" and "the book advanced" are the same statement. On a socket they are not. A server can keep sending bytes that decode to nothing — a shape the parser rejects, or nothing but summary frames — and a watchdog armed on arrival would sit happily while the ladder froze, still reading Live. That is the exact output invariant #5 exists to forbid, and a trace file cannot contain it.

So FeedTask arms its watchdog on an event reaching the book. The cost of doing so had to be measured rather than argued, because a stricter rule that fires on healthy data is worse than the bug it fixes — and over both committed captures the worst healthy gap turns out to be identical whichever way it is counted:

Counting…FramesWorst healthy gap

They agree because the book stream is the dense one at ~12 Hz and the 2 Hz summaries never fill a hole the book frames left, so the 1.6× margin under 1000 ms survives untouched. The 2026-08 re-measurement re-ran the same three-way count over 20,418 frames and found the same thing — all three rules agree on a 391 ms worst gap — and then over a deliberately throttled socket at the board's own message rate, where they finally separate: 141 ms by frame arrival, 250 ms by event, 594 ms by book event. That separation is the firmware's stricter rule earning its keep, and it is still 1.68× inside the threshold. The two definitions differ only on inputs the traces do not contain — which is precisely why the divergence is worth writing down rather than quietly having. Aligning the host driver is a candidate for M4; it was not done at stage C because that driver is golden-covered and stage C's scope was firmware.

What the board can now say about its own silence

The re-measurement above ends with the board holding a number the desk cannot reproduce — a 2,461 ms silence with the socket up — and no way to say anything more about it. worst_gap is a single high-water mark, and a maximum is the one sample guaranteed to be an outlier: it cannot distinguish one reconnect artefact from a population of 1.2 s stalls, and it cannot say whether the hole is in the bytes arriving or in the pipeline that consumes them. Those have different causes and different fixes, so the next firmware session's output is an instrument rather than a patch.

Two clocks, two histograms, one reading. Every whole WebSocket message is stamped inside the client's callback as it finishes arriving, and again when the event it carries reaches the book. FramePipeStats::arrival_gaps buckets the first series and FeedTask::Stats::event_gaps the second, on shared edges whose 1000 ms boundary is the watchdog threshold — so the count above that edge is literally the number of occasions the panel had grounds to grey. arrival_to_event bridges them for a single message, with worst_queue_wait_us splitting off the part spent waiting for the feed task to be scheduled at all.

cleanfillsthe board — the bytes arrived and the pipeline sat on them

The load-bearing detail is on the arrival side and it is one line of ordering: a message dropped for want of a free slot is counted as an arrival anyway. Slot exhaustion is caused by the feed task being slow, so an arrival series that recorded only the messages the board managed to keep would print feed-side starvation as a hole in the network — the exact misreading the split exists to prevent. That rule lives in FrameReassembler::finish(), which is ESP-IDF-free and therefore host-tested beside the bucketing arithmetic; the bucket boundaries are pinned by a test rather than by a comment, because an instrument that is wrong by one column does not fail, it sends a bench session after the wrong candidate.

Where that table over-claimed, and the signal that replaces it

The two steady-state runs it was built for came back with the split refusing to split: connects=1 and sock_gaps=0 across whole runs that still logged 17 book-holes in 11 minutes (power save off) and 25 in 10.5 minutes (on), each a genuine 1–2.5 s window. The socket never dropped and Anvil — an unconditional ~80 ms republisher — never stopped. The board simply received the stream in bursts, and both histograms filled together.

Read against the table above, that says "transport". It does not, and the reason is the first row's premise: the arrival stamp is not the wire. It is taken in WsTransport::on_event, inside esp_websocket_client's own task, which is already downstream of the Wi-Fi driver, lwIP, the socket read, the TLS record decrypt and the esp_event dispatch hop. A hole in arrival_gaps therefore means no complete message was handed to our callback for a second — equally consistent with a dry socket and with that task not being scheduled on a busy Core 0. The split is real, but the line it draws is at the FramePipe queue hop, not at the antenna.

The second reason is upstream and not ours: Anvil's per-socket coalescing sheds book frames whenever a socket backs up (measured 2026-08-09: a client throttled to a quarter rate receives 4× fewer messages and is never silent for longer than one drain interval). So shedding is a symptom of the board falling behind rather than an independent cause, and "Anvil shed it" and "Wi-Fi delayed it" surface identically as no book frame for two seconds. The un-entangled question is not where the hole appears in the pipeline; it is whether Core 0 had the headroom to drain the stream at all.

That needs a signal from outside the data path, and as of 2026-08-10 the board carries three (firmware/src/stall_probe.hpp, core_idle.*): per-core idle across exactly the window that greyed the panel, the shape of the recovery that ended it, and the rssi at the time. Idle is measured from inside each core's own idle task — FreeRTOS run-time stats are compiled out of the precompiled Arduino framework, the fourth capability this vintage has decided here — by differencing the core's cycle counter across passes through an idle hook that returns false, which is what keeps the hook being called instead of the core sleeping.

The wire seq earns its place here for the one thing it can do. It is a global counter and unusable for ordering (§04), but its rate is a clock: a frame ending a hole with a seq step of about one is an old frame that was sitting somewhere, and one with a step of roughly rate × hole is a fresh frame whose predecessors were never sent to us. The board prints both the step and the prediction, so the reading is checkable rather than asserted — as are the verdicts, which print beside the idle figure and the baseline they were derived from. Nothing branches on any of it.

The other failure, which deliberately does nothing

06 How any of this is proved

#6 no merge without replay coverage #7 allocation-free, measured

The harness is not test scaffolding around the engine; it is the host stand-in for the M3 firmware feed task, and it is deliberately the only place the engine is wired together. That is why the goldens and the console ladder can never disagree about what a trace means — there is one assembly, and both read it.

One detail carries more weight than its size suggests. TraceReader hands the adapter a string_view sliced out of the capture line by a string-aware scanner, not a re-serialised object. The adapter sees exactly the bytes the server sent, key order and spacing included — otherwise the harness would be validating a parser against its own output.

What the gate actually runs

cmake --workflow --preset host configures, builds and tests in one step (host-mingw is the Windows MinGW-w64 equivalent; the two presets share a binary directory, so switching between them needs build/host cleared). Nine ctest entries run; the main doctest binary carries 80 cases across eight files, and a second doctest binary re-runs the parser-facing subset of them against the other implementation of the parse seam.

Invariant #7 is not asserted in prose anywhere that matters — it is measured. alloc_probe replaces global operator new in the test binary, so "allocation-free steady state" becomes: take the counter, run the feed path, take it again, require no change. Two cases do exactly that in dc_tests, one over the book and one over the channel round trip.

M3 stage B pointed the same probe at the last piece that was still exempt. In dc_tests_streaming the whole feed path — verbatim wire bytes → streaming parser → adapter → book → SnapshotChannel::publish → consume — runs over every frame of both committed traces, with the counter latched at the instant the first snapshot is published, which is the exact boundary the invariant names. Across 2,694 frames and 2,341 published events it moves by zero. The trace is read and sliced into string_views before the window opens, because the file I/O and the NDJSON reader allocate freely and would drown the signal — which is also, not coincidentally, the shape the firmware net task will have: a fixed reassembly buffer handed to the parser as (ptr, len).

The whole engine as instantiated for one symbol is 20,480 bytes — adapter, book and channel together — against 512 KB of internal SRAM on the S3, before the HUB75 framebuffer takes its share. Neither number is close to a constraint, which is the point of having measured them: the argument for the dense window at M4 has to be made on delta-venue correctness, not on this.

What the parser costs the target

RAM is the wrong axis for the streaming parser: it has none. Compiled with the PlatformIO xtensa GCC 8.4 at -Os -fno-exceptions -fno-rtti, the whole translation unit is 5,861 bytes of .text, 0 of .data, 0 of .bss — and no .init_array, so it has no global state and no static constructors to order. Its working state is one stack frame — a cursor, a few scalars and a 64-byte token scratch — writing into the adapter's existing AnvilFrame, so parsing an 8 KB book frame costs no storage that was not already counted in the table above.

Stack is the figure that actually matters on a FreeRTOS task, and it is bounded and input-independent. -fstack-usage reports every frame as static — no alloca, no VLA — with the largest at 272 bytes (parse_anvil_frame, which the optimiser inlines the whole top-level walk into, scratch buffer included). The call graph is acyclic because the value skipper is iterative, so the deepest chain is fixed at about 600 bytes: a frame nested 5,000 brackets deep costs exactly what a flat one does. That is the property that makes the 64-container cap a memory decision rather than a crash-avoidance one.

The more useful measurement is the undefined-symbol list of that object, because it is the invariants stated as link errors that did not happen: __ashldi3 __divdi3 __lshrdi3 __moddi3 __udivdi3 memcmp memset strlen. No _Znwm, so nothing allocates. No __cxa_* or _Unwind_*, so nothing throws. Nothing from ESP-IDF. The four *di3 helpers are 64-bit integer arithmetic — and one of them is worth watching: wire_qty_to_steps does an int64_t divide and modulo per level, so ~250 levels at 12 frames/s is ~3,000 software 64-bit divisions a second on the LX7. That is inherited from M1's shared scaling and is identical in both parsers, so it is not a stage B regression, but it is the first thing to look at if the feed task ever needs headroom. qty_step is 1 for every venue we consume.

08 Where this design is carrying load it has not been asked to bear

the section to argue with

Everything above describes code that works and is green. This section is the honest counterweight: twelve places where the current shape is either unenforced, speculative, or about to be tested by a milestone that does not exist yet. Each is stated with what would break it and what resolves it.

0 · engine/ is proven host-buildable, and now target-buildable too

This entry used to be implicit and unenforced. The generated per-header check proved engine/ compiles on the host; nothing proved it compiles for the ESP32-S3, and the two genuinely disagree — the target toolchain that espressif32 6.5.0 pins is xtensa GCC 8.4, which does not accept -std=c++20 at all and whose libstdc++ lacks <span>, <ranges>, <concepts>, <bit>, floating-point from_chars, and constexpr algorithms. A header can be valid on the desk and reject on the board, silently, until M3 tries to link.

dc_engine_target_check now compiles the same generated TUs with the PlatformIO xtensa compiler when it is installed, at ESP-IDF-shaped flags. All eight engine headers pass; the hot path costs 1541 B of .text at -Os. The remaining strain is that the check is optional — a contributor without PlatformIO gets a host-only guarantee and a STATUS line saying so.

Resolves: CI that has the toolchain installed, so the target half is never the skipped half

1 · LevelSpan is a lifetime contract with no compiler behind it

The rule — copy before you defer — is enforced today only by the fact that a single consumer exists and it copies immediately. Nothing stops an M3 feed task from pushing a FeedEvent onto a queue, and if it does there is no diagnostic, no sanitiser hit on the common path, and a ladder that is subtly wrong rather than obviously broken. Invariant #7 forbids the obvious fix, since a guard type would stop FeedEvent being trivially copyable.

Resolves: a debug-build generation counter on AnvilFrame, asserted in LevelSpan — no release cost, no layout change

2 · SnapshotChannel was a claim; M3 stage A made it a mechanism

Until stage A this was a single slot behind two plain uint32_ts, with the header saying plainly that concurrent use was undefined and the M1 test exercising it single-threaded only. It is now three DisplaySnapshot slots and one atomic word: publish and consume each swap their slot into that word with a single exchange, so the writer's slot, the reader's slot and the ready slot are always three distinct objects and neither thread ever touches the frame the other is using.

Three rather than the two the constitution's wording implies, and that is the part worth arguing with. A seqlock and a two-slot buffer both let the reader copy a slot the writer is writing and then discard the result — the tear happens; the version check only stops it being drawn. Measured both ways: a seqlock of exactly that shape delivered 4.8 M frames with zero tears reaching the consumer on x86 GCC 10 -O2, and ThreadSanitizer flagged it on the first frame. So the case against it is not that it misbehaves on today's compiler; it is that the copy is a data race, and the only way to have both a seqlock and a clean report is a suppression sitting on the one cross-core path, on a target compiler generation nobody here controls. The third slot costs 2,352 bytes (§07).

Evidence: harness/tests/test_snapshot_channel.cpp races two threads over 100,000 frames whose every field is stamped from the frame's own version, so a delivered frame is either whole or provably spliced and the checker names the field where it split; harness/tests/tsan_clean.txt is the committed ThreadSanitizer report. Both mutation-verified — collapsing the slots back to M1's one fails at version 12.

Resolves: done — the residual strain is that TSan needs Linux, so the report is refreshed by hand via harness/tsan.sh rather than by the host gate

3 · There is no VenueAdapter type

The architecture diagram names one; the code has AnvilAdapter with a template Sink, no base class and no concept. That is the right call for invariant #7 — no virtual dispatch on the feed path — but it means "what an adapter is" is currently convention. Kraken at M4 is the forcing function: either a C++20 concept pins the shape, or two adapters drift apart with nothing to catch it. This is the largest open design question in the repo.

Resolves: decide at M4, before the second adapter has behaviour worth preserving

4 · The book retains 8,552 bytes to publish 1,168

kBookCapacity is defined as kMaxSnapshotLevels — 256 per side — while the panel renders 27. The justification is the M7 zoom mode, which is four milestones away and may never take that form. The coupling itself is defensible (a snapshot the adapter accepted can never be truncated a second time), but the value is speculative capacity.

Resolves: cheap to leave; revisit only if S3 SRAM gets tight against the framebuffer

5 · Book's face has never met a delta

M4 requires the tick-indexed dense window to land "behind this same apply()/publish() face". That is an untested assumption. Re-anchoring by bounded copy, a cold tail in a map, and CRC verification are all things a snapshot-only book never had to express, and if the face does not survive them, this section of the design is what changes.

Resolves: M4 — and a face change there is a §9 amendment, not a refactor

6 · Every event republishes the whole ladder

publish() bumps version_ unconditionally, so a trade-only event produces a new version and the render side redraws even though no level moved. At Anvil's ~15 events/s that is comfortably under the 30 fps target and costs nothing worth reclaiming. It becomes a real question only at a venue with a much higher per-event rate.

Resolves: nothing to do now; note it before M5's Binance diff stream

7 · format_px returns a std::string

The console ladder allocates freely, which is correct for the display edge on a desk. But format_px lives in the harness header a firmware renderer will be tempted to imitate, and the target must use format_scaled into a stack buffer instead. Nothing currently enforces the distinction, and the alloc probe covers the feed path, not the render path.

Resolves: M3 stage D — extend the alloc probe across the render side too

8 · The harness reads meaning into Seq == 0

StaleEpisode::gap_seq == 0 is used as "not yet set", which is only safe because AnvilAdapter::next_seq_ starts at 1 and 0 is reserved for "no event yet". That is a real convention, documented in the adapter — but it is an engine convention that harness logic now depends on, across a boundary neither file names.

Resolves: a one-line comment, or an explicit optional; low stakes, worth knowing

9 · Two parsers now have to stay the same thing

M3 stage B closed the last allocating hole on the feed path — the parser is now allocation-free, measured over both traces with global operator new counted, and it compiles for xtensa GCC 8.4 with no undefined symbol implying a heap, an exception or ESP-IDF. That part is settled. What it bought in exchange is a new obligation: one declaration with two definitions is two chances to be right.

The reference is not a spec written down anywhere; it is nlohmann 3.11.3's behaviour, including the parts Anvil never exercises. Duplicate keys resolve last-wins because that is what a std::map filled through operator[] does. An integer too large for uint64_t is a float, so a quantity of 99999999999999999999 is a shape error rather than a saturated number. A NUL byte ends the document even mid-buffer. None of that is written in anvil_frame.hpp, and all of it is load-bearing, because the adapter files the three failure statuses into three different counters and the counters are goldens.

The mitigation is that the equivalence is executed, not reviewed: test_parser_equivalence.cpp is compiled into both binaries and holds both implementations to one table, covering escapes, surrogate pairs, over-range integers, invalid UTF-8, error precedence under reordered keys, and duplicate keys at every level. Three divergences remain, deliberately, and are asserted on both sides of their boundary in test_streaming_parser.cpp — a one-sided test would still pass if the limit silently fell — so that a later session cannot quietly close one, or shrink one, without reading why it was opened. They are: a single skipped value may nest 64 containers and not 65 (the container stack is one uint64_t, which is what keeps the skipper iterative and heap-free); an escaped price whose unescaped form reaches 65 bytes is BadPrice rather than its value; and the open band between DBL_MAX and 1e309 is treated as finite.

How much that mitigation is worth was measured rather than assumed. Three independent agents ran roughly 2.4 million differential inputs through both implementations — byte-mutated real frames, exhaustive truncation at every offset, all 65,536 \uXXXX escapes, all 65,536 two-byte raw sequences, every permutation of the top-level member set, integer and double boundary sweeps — and found no disagreement outside those three. The sharpest evidence is a corpus built so that none of the three can fire (nesting capped at 20, no literal near 1e308, every escaped string under 40 bytes) replayed across 24 SymbolSpec configurations: 567,842 records, zero differences.

Resolves: never fully — it is the standing cost of the seam. Keep the equivalence table growing with every wire surprise; if the two ever have to diverge on something Anvil can actually send, that is a §9 amendment, not a patch

10 · There are now two definitions of "the feed has stopped"

The host replay driver greys on a hole between frames; the M3 stage C firmware greys on a hole between events reaching the book (§05). Both use 1000 ms, and on every captured input either has ever seen they agree exactly — 640 ms at M0, 391 ms on the 2026-08 re-measurement, identical under all three counting rules both times. They differ where a trace file cannot go: bytes that arrive and decode to nothing.

The 2026-08 work found the first input on which they do separate, and it is not a malformed frame — it is a slow client. Against a socket throttled to the board's message rate the worst silence is 141 ms counted by frame arrival and 594 ms counted by book event, because Anvil sheds coalesced book frames to a backed-up consumer while the 2 Hz summary broadcast keeps arriving. So the weaker rule is not merely less strict in theory; on a real stream to a real device it under-reports the thing the panel is actually showing by 4×. That strengthens the case for one rule, and it means the alignment is no longer golden-neutral by inspection — the M4 session has to measure it on the throttled trace, not only on the two committed ones.

The firmware's rule is the better one — it is the version that cannot leave a frozen ladder reading Live — but having two is a real cost, because the goldens now pin the weaker rule and the panel runs the stronger one, so the harness can no longer be said to preview the firmware exactly. The right end state is one rule in both places.

Resolves: M4 — move the host driver onto the event-armed rule. Golden-neutral on all three committed traces (the worst gap is identical whichever way it is counted: 640.2 ms at M0, 391 ms in 2026-08), but no longer neutral in general — a throttled stream separates the two rules 4× — so the M4 brief owns a throttled trace as well as a re-pin, and it is a change to golden-covered code that belongs in a brief, not in a firmware stage

11 · Invariant #7 is now two claims, because the transport is not ours

Every earlier statement of "allocation-free steady state" was about code in this repo, and could be proven absolutely: alloc_probe counts zero over both traces, and the streaming parser's xtensa object has no undefined operator new to call. Stage C is the first time the invariant met a library nobody here wrote, and it loses. esp_websocket_client dispatches every event through esp_event_post_to, which heap-copies the 28-byte payload and frees it when the handler returns — about 37 balanced calloc/free pairs a second at three DATA events per book frame.

So the invariant now reads differently either side of the boundary: strict for the engine, "no net allocation and no fragmentation drift" for the transport (ARCHITECTURE §9). That is defensible — bounded churn of one fixed-size block threatens neither determinism nor a heap that must survive a week on a desk — but it is a weaker sentence than the one the constitution started with, and weaker sentences drift. The instrumentation is honest about its own limits: ESP-IDF heap tracing is compiled out of the precompiled framework, and the low-water mark is a since-boot minimum that cannot see steady churn at all, so heap_probe detects a leak or fragmentation and says so rather than claiming to test the invariant.

Resolves: not by tightening the words. Either accept the split permanently, or move to pure ESP-IDF where heap_trace_start exists and the claim can be measured rather than reasoned — which is the same platform decision stage C deferred for the framework, and should be made once, for both reasons together

12 · Something stalls the board's feed for seconds, and only the panel can see it

The desk half of this project is measured to death and the board half is measured by three counters and a serial line. That asymmetry has now produced its first real defect: on the bench the panel greys every 15–20 s with the socket up (wd_gaps=5 in 90 s, sock_gaps=0, connects=1), worst silence 2,461 ms — and nothing at the desk end of the same LAN reproduces it. Anvil runs at 17.02 frames/s with a 391 ms worst gap; a socket deliberately throttled to the board's own 8.30 msg/s still has a worst book-event silence of 594 ms and trips the watchdog zero times in four minutes. Whatever costs the board those seconds happens on the board.

It very nearly became an architectural change instead of a bug. The obvious reading of "the board sees ~6 msg/s where M0 saw 15.5" is that the venue slowed, and the fix for that is to raise kRxWatchdogMs — which would have suppressed the symptom, moved a committed golden, weakened the invariant-5 proof, and left a 2.5 s freeze of the feed pipeline in place, reading Live. What stopped it was measuring the premise before acting on it. The general form is worth keeping: a threshold that fires is evidence about the thing it watches, not about itself, and the constant is the last place to look.

The instrumentation was the real gap, and it is now closed. worst_gap is a single high-water mark with no distribution behind it, so the board could report that it saw 2,461 ms but not how often, nor whether the hole was in arrival or in decode, nor whether the feed task was starved or the socket was quiet. Every question the desk answers in one command was unanswerable on the device that has the problem. As of 2026-08-09 the board carries the arrival and event gap histograms, the arrival→event latency and the queue-wait split described in §05 — 128 bytes of static storage, allocation-free, and the bucketing host-tested. The measurement itself is still owed: it takes a ≥10-minute bench run with no deliberate disconnects, which is the owner's, and until then this strain point is instrumented but not diagnosed.

One candidate was narrowed without the board, and it is the one the characterisation brief expected to be cheapest: Wi-Fi modem sleep. Arduino-ESP32 2.0.14 does default it on for the S3 (_sleepEnabled = WIFI_PS_MIN_MODEM), but this firmware has called WiFi.setSleep(false) since the stage C draft, and after WiFi.mode(), which the shipped source says is the order that makes it take effect. So the experiment was not "does turning it off help" — it was whether turning it off was ever taking effect, and whether turning it back on reproduces the stall. It does not reproduce it and it does not remove it: 17 holes in 11 minutes with power save off, 25 in 10.5 minutes with it on, worst 2,461 ms and 1,893 ms respectively. Modem sleep is not the mechanism.

The bench ran, and the split the instrument was built around could not decide it. Both runs held connects=1 and sock_gaps=0 while arrive and event filled their >1 s buckets together — which the 2026-08-09 verdict table reads as "transport", and which is an over-claim on two counts, both now written into §05. The arrival stamp is taken inside esp_websocket_client's task, downstream of the Wi-Fi driver, lwIP and the TLS decrypt, so an arrival-side hole does not exclude a busy Core 0; and Anvil's per-socket coalescing sheds to a slow consumer, so "the server stopped sending" and "the board stopped keeping up" are the same observation seen from two ends. The two candidates are entangled by construction, and no amount of instrumenting the data path separates them.

So the 2026-08-10 instrument steps outside the data path: per-core idle across each hole window, the recovery shape that ended it, and rssi (stall_probe.hpp, core_idle.*; +640 B RAM, +4.2 KB flash, still allocation-free, and the classification host-tested in test_stall_probe.cpp because a verdict that is wrong reads exactly like one that is right — the property test there caught the hole log handing out a record that was still being written, which would have printed an unclassified verdict as a real one). Its own load-bearing detail is what happens when it cannot measure: a probe that failed to register reports idle as unknown, never as zero, because zero would classify every hole in the run as board-bound and read as an unusually decisive result.

It is not free of perturbation and does not pretend to be. Keeping the idle hook being called means the idle task does not execute waiti, so an idle core spins instead of sleeping — acceptable on a mains-powered object with CONFIG_PM_ENABLE off and a priority-0 idle task that cannot delay real work, and reversible with -D DC_IDLE_PROBE=0 so a suspicious result can be re-run without the instrument. Whether it ships past the characterisation is a stage D decision, not a settled one.

Resolves: verdict instrument landed 2026-08-10; the diagnosis needs one more ≥10-minute -e depthcharge run with connects=1. It picks the next brief outright: board-bound (Core 0 starved) opens the lever bundle — esp_websocket_client buffer_size, the LWIP TCP window (CONFIG_LWIP_TCP_WND_DEFAULT is 5,744 B, smaller than one 8.7 KB Anvil book frame), WS-task priority and core — each re-benched against this instrument with near-zero steady-state >1 s holes as the bar; link-bound (Core 0 idle) leaves firmware entirely for 2.4 GHz channel, placement and rssi correlation, with Anvil's incremental-L2 feed staying on the Anvil backlog for M4/M5. What is already excluded: modem sleep (both arms measured), Anvil's cadence (17.02 frames/s, 391 ms worst gap at the desk), and the socket (connects=1)

09 Keeping this true

hand-off protocol

A design document that drifts is worse than none, because it is believed. This one is a single file in the repo, so it diffs with the code it describes, and it is deliberately scoped to things that are expensive to rediscover: which type crosses which boundary, what a call actually does in order, and where the design is under strain.

It does not restate ARCHITECTURE.md. That file is the constitution and stays the source of truth for the invariants and for any decision with architectural weight; this file draws the code that implements them. When the two disagree, the constitution wins and this file is the one that is wrong.

What triggers an update

  • A class gains, loses or renames a member that appears in a diagram here.
  • A call order changes — anything a sequence diagram would now draw differently.
  • A new type crosses an existing boundary, or a new boundary appears.
  • A strain point in §08 is resolved, newly created, or turns out to be wrong.
  • A milestone completes: the status strip and the dashed boxes move.

  • §03 — the streaming parser box loses its dashes; dc_engine_anvil becomes the harness reference only. — done at stage B. It also grew a third box the queue did not predict: anvil_scaling.hpp, the conversion both parsers share, which is where invariant #3 is actually held.
  • §04 — SnapshotChannel gains its second slot and an atomic version — done at stage A, and it took a third slot rather than a second; §07 reads 3,528 bytes, not the ~2,344 predicted here.
  • §08 — strain point 2 closed at stage A; 9 opened at stage B (two parsers, one meaning); 10 and 11 opened at stage C (two definitions of "stopped"; invariant #7 split across a boundary we do not own); 12 opened by the 2026-08-09 watchdog re-measurement (the board stalls for seconds and only the panel can see it), half-closed the same day, and re-opened on 2026-08-10 when the bench showed the arrival-vs-event split could not decide it — the two candidates are entangled through Anvil's shedding and through where the arrival stamp is taken, so the verdict now rests on per-core idle instead; 7 should close at stage D; 1 and 3 will not.

When the stall is found and fixed, the histograms stay (they are how the next one gets found) but both verdict tables become history.
