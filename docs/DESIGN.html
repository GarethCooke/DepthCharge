01 The shape of the whole thing

#1 host-buildable #2 one boundary type #8 one writer

DepthCharge is a pipeline with swappable ends. Bytes arrive from a replay file on a desk or a TLS WebSocket on an ESP32-S3; pixels leave to a terminal or to a HUB75 DMA driver. Between those two swaps sits engine/, which is the same translation units in both cases — not a port, not a shared interface, the same code.

That is the bet the whole project makes, and it is enforced rather than asserted: CMake generates one translation unit per engine header that includes only that header, so the moment an ESP-IDF include leaks into engine/ the host build fails, because the host has no such header to find.

What the build actually produces

The CMake targets encode the same separation, which is what makes the claim checkable rather than aspirational. dc_engine is an INTERFACE library — header-only, so nothing can be compiled into it with the wrong flags. dc_engine_anvil is deliberately its own static library because it is the single target that touches nlohmann/json, and therefore the single target that must not reach the microcontroller. Since M3 stage B it has a twin, dc_engine_anvil_streaming, which is the same declaration implemented without a parser library at all — and which pointedly does not link dc_vendor, so the separation is enforced by the linker rather than asserted in a comment.

There is one deliberate crossing in the other direction: dc_tests puts firmware/src on its include path to compile test_frame_reassembler.cpp. That is a header — the WebSocket reassembly state machine, written free of ESP-IDF precisely so it can be tested here — and no firmware .cpp is ever compiled on the host. It is the only piece of stage C that is new logic rather than engine code or a thin wrapper over an Espressif call, and a replay trace cannot exercise it, because the capture tool's WebSocket library reassembled the chunks before writing the line.

02 The vocabulary that crosses the boundary

#2 one boundary type #3 integer ticks only #7 allocation-free

FeedEvent is a plain aggregate with no methods and no ownership. Four kinds share one flat layout, and which fields mean anything is a function of kind. That is a tagged union written without a union — deliberately, because a static_assert on trivial copyability is what lets the render hand-off be a memcpy and lets the whole feed path avoid the heap.

Prices are int64_t ticks and quantities are int64_t steps. There is no floating-point number anywhere in the type, and the conversion from the wire's decimal strings happens in parse_scaled, which refuses to round: a price carrying more precision than the declared scale is a reported error, never a quietly truncated level.

The lifetime rule, which the compiler does not enforce

A Snapshot carries 84–126 levels per side across the committed baseline trace — measured, not assumed. Putting them in FeedEvent by value would make the boundary type kilobytes wide; putting them in a container would make it allocate. So the levels stay in the adapter's reusable AnvilFrame and travel as two raw pointers, valid for exactly the duration of the sink call.

03 The adapter, and the seam inside it

#2 venue mess quarantined #3 no float touches a price #7 no virtual call, no allocation

AnvilAdapter owns every Anvil-specific decision so that Book owns none. Three of those decisions are load-bearing and each one is a place a naive implementation would have gone wrong:

  • The wire seq is decoded and then ignored. Anvil's seq is one global counter shared by every ticker and frame type, so a single socket's subsequence runs backwards — 42 times in five minutes, measured at M0. The adapter synthesises its own dense Seq from receive order and keeps the wire value only as a diagnostic counter. It can therefore never emit Gap{SeqGap}, which is safe only because Anvil's book frames are idempotent full replaces.
  • snapshot and book are the same event. Both become FeedEvent::Snapshot. book is not a delta and treating it as one would corrupt the ladder silently.
  • A malformed frame is dropped, not gapped. Anvil republishes the whole book every ~80 ms, so one bad frame self-heals within a refresh; greying the panel for it would be dishonest in the opposite direction. A systematic failure shows up as a stalled ladder plus a non-zero parse_errors count.

One declaration, two definitions, chosen by the linker

The only genuinely environment-specific work in the adapter is turning JSON bytes into fields. That work sits behind a single free-function declaration, and the implementation is selected by which static library a binary links. It is the cheapest possible seam — no virtual call, no template, no runtime branch — and M3 stage B is where it earned its keep: the second definition landed with zero changes to the adapter, the book, the contract types or the goldens.

What the seam does not cover is the conversion arithmetic. Both parsers include anvil_scaling.hpp and call the same price_text_to_ticks, wire_qty_to_steps, aggressor_from_text and kind_from_type. That split is deliberate and it is where invariant #3 is actually defended: a hand-rolled rewrite fails loudly on JSON structure, but a reimplemented price conversion would fail quietly, one tick at a time, and look like a market difference. Each parser's job stops at finding the token's bytes.

A healthy book frame, end to end

04 The book, and why it is barely a book

#3 integer ticks #5 stale is first-class #7 fixed capacity #8 one writer

Anvil publishes a full top-N replace every ~80 ms. Against a venue like that, book maintenance is not a data-structure problem — "adopt the latest snapshot" is the entire engine, plus a ring of recent prints. The tick-indexed dense window that the architecture describes is real work, but it is M4 work, and building it now would mean building it against no delta stream to test it with.

So Book today is two fixed arrays, a ring, and a status flag. What makes it interesting is not the storage; it is the four ways apply() can end, and the fact that one of them is deliberately impossible-in-practice.

Two states, and only one way back

The asymmetry is the design. Four different things drive the book into Stale; exactly one thing brings it out, and that is a fresh Snapshot. A trade print arriving during an outage is still real tape and is still recorded — but it does not clear the flag, because it says nothing about whether the resting levels are still true.

reject_delta() is the interesting one. Anvil never sends a delta, so on the only venue that exists this branch is unreachable. It exists because the alternative — silently ignoring an event kind the book cannot apply — would produce exactly the failure mode the project is built to prevent. It is a tripwire for a future adapter bug, and it costs one enum comparison per event.

05 When it goes wrong

#5 stale is a rendered state #6 replay coverage

Anvil emits no error frame and no gap frame. Absence of data is the only signal there is, which means the disconnect is synthesised by the transport — and the harness has to synthesise it too, or the host replay would be an analogy rather than a preview.

Two rules were available for a capture file with no disconnect marker. "A mid-stream snapshot means we reconnected" was rejected: the gap would be raised in the same breath as the snapshot that clears it, so the book would never actually be stale and the invariant-5 proof would be vacuous. The rule chosen instead is a watchdog, and the number is measured rather than picked — across two five-minute captures the worst healthy inter-frame gap was 640 ms against a ~70 ms median, so 1000 ms sat 1.6× above the worst healthy silence and 4.5× below the observed drop.

That derivation has since been re-measured rather than re-derived, and it held. M3 stage C put the firmware on a bench and the panel greyed every 15–20 s on a socket that never dropped, with the board reading ~6 messages/s against M0's 15.5 — which reads exactly like a server that has slowed until healthy silence outgrew the threshold. It is not. A fresh twenty-minute capture (20,418 frames) has Anvil faster and steadier than at M0 — 17.02 frames/s, worst gap 391 ms — so re-deriving from current cadence would have moved the threshold down, to ~626 ms, and made the false greys worse. 1000 ms now stands 2.6× above the worst gap in twenty minutes and 5.3× above p99.9, on three times M1's sample.

The board's low message rate is real, and it is backpressure rather than cadence. Corrected 2026-08-11 (this paragraph caught up 2026-08-16): this used to read Anvil sheds to a slow consumer, and sheds evenly — it does not. Anvil queues, without bound, and the conclusion below survives the correction intact, because a queued stream is regular: a client throttled to a quarter of the server's rate receives every frame, late, delivered at its own drain cadence, so it is still never silent longer than one drain interval. Confirmed in Anvil's own source and measured by seq-matching against a reference clock rather than by cadence (strain 17). The distinction to keep straight, because both halves are true: Anvil does coalesce — on its 70 ms publish tick, which bounds the rate it produces — and its per-socket send queue (Crow's write_buffers_) has no cap and no drop, so nothing bounds the total once a socket stalls. Throttle a desk socket to the board's own 8.30 msg/s and measure it under the board's own book-event rule and the worst silence is 594 ms, with zero watchdog trips in four minutes; the board shows 2,461 ms. So the multi-second holes are board-side and the watchdog is reporting them honestly. Raising the threshold would have hidden a real 1–2.5 s freeze of the feed pipeline — the frozen-ladder-reading-Live outcome invariant #5 exists to forbid. The constant did not move; the measurement became a golden so that a real future cadence change goes red on the desk instead of grey on the panel (ARCHITECTURE §9, 2026-08-09; harness/replay/NOTES.md M3 addendum).

The detail that makes the stale window real is the timestamp. The gap is dated at prev_rx + 1000 ms — the moment the watchdog would have fired — not at the moment the next frame eventually arrived. In the committed reconnect trace that turns an instantaneous blip between two frames into 3.47 s of grey.

The firmware watches something slightly different, on purpose

M3 stage C implements the same 1000 ms rule on the board — and then arms it from a different event, which is the one place the two halves of this project deliberately disagree. The host driver fires on a hole in rx_ns between any two frames, which is exact for a trace file: in a capture every frame parses, so "a frame arrived" and "the book advanced" are the same statement. On a socket they are not. A server can keep sending bytes that decode to nothing — a shape the parser rejects, or nothing but summary frames — and a watchdog armed on arrival would sit happily while the ladder froze, still reading Live. That is the exact output invariant #5 exists to forbid, and a trace file cannot contain it.

So FeedTask arms its watchdog on an event reaching the book. The cost of doing so had to be measured rather than argued, because a stricter rule that fires on healthy data is worse than the bug it fixes — and over both committed captures the worst healthy gap turns out to be identical whichever way it is counted:

What the board can now say about its own silence

The re-measurement above ends with the board holding a number the desk cannot reproduce — a 2,461 ms silence with the socket up — and no way to say anything more about it. worst_gap is a single high-water mark, and a maximum is the one sample guaranteed to be an outlier: it cannot distinguish one reconnect artefact from a population of 1.2 s stalls, and it cannot say whether the hole is in the bytes arriving or in the pipeline that consumes them. Those have different causes and different fixes, so the next firmware session's output is an instrument rather than a patch.

Two clocks, two histograms, one reading. Every whole WebSocket message is stamped inside the client's callback as it finishes arriving, and again when the event it carries reaches the book. FramePipeStats::arrival_gaps buckets the first series and FeedTask::Stats::event_gaps the second, on shared edges whose 1000 ms boundary is the watchdog threshold — so the count above that edge is literally the number of occasions the panel had grounds to grey. arrival_to_event bridges them for a single message, with worst_queue_wait_us splitting off the part spent waiting for the feed task to be scheduled at all.

Where that table over-claimed, and the signal that replaces it

The two steady-state runs it was built for came back with the split refusing to split: connects=1 and sock_gaps=0 across whole runs that still logged 17 book-holes in 11 minutes (power save off) and 25 in 10.5 minutes (on), each a genuine 1–2.5 s window. The socket never dropped and Anvil — an unconditional ~80 ms republisher — never stopped. The board simply received the stream in bursts, and both histograms filled together.

Read against the table above, that says "transport". It does not, and the reason is the first row's premise: the arrival stamp is not the wire. It was taken in WsTransport::on_event, inside esp_websocket_client's own task, which is already downstream of the Wi-Fi driver, lwIP, the socket read, the TLS record decrypt and the esp_event dispatch hop. A hole in arrival_gaps therefore meant no complete message was handed to our callback for a second — equally consistent with a dry socket and with that task not being scheduled on a busy Core 0. The split is real, but the line it drew was at the FramePipe queue hop, not at the antenna.

The owned client (2026-08-14) moves that line one hop upstream and no further. The stamp is now taken on the instruction after the esp_tls_conn_read that produced the bytes, on a task this firmware created and pinned to Core 0 — so the esp_event dispatch hop and the unpinnable library task are both out of the measurement, and a hole on the arrival side can no longer be that library's scheduling. What remains between the antenna and the stamp is the Wi-Fi driver, lwIP and the TLS record decrypt, which are still not ours and still not zero. The sentence above stays true in shape: the arrival stamp is still not the wire, it is just closer to it.

The second reason is upstream and not ours. Anvil's per-socket coalescing sheds book frames whenever a socket backs up (measured 2026-08-09: a client throttled to a quarter rate receives 4× fewer messages and is never silent for longer than one drain interval). That sentence is withdrawn — ARCHITECTURE §9, 2026-08-11: Anvil does not shed to a slow consumer, it queues. The 2026-08-09 probe was honestly run and its numbers are all still true; what was wrong was the sentence written under them, because a measurement of rate or of inter-message gap cannot distinguish a shed stream from a queued one. Seq-matching against a reference clock settled it: every frame kind thinned by the same 25%, lag rising linearly to 111 s over 150 s with no plateau, ~12.4 MB implied still queued for one socket. The shape of the conclusion survives and is if anything stronger — a thinned stream is a symptom of the board falling behind rather than an independent cause, and "Anvil held it back" and "Wi-Fi delayed it" surface identically as no book frame for two seconds. The un-entangled question is not where the hole appears in the pipeline; it is whether Core 0 had the headroom to drain the stream at all — and by 2026-08-16 the answer is measured and is yes (strain 19: feed 0% at every hour of a day).

That needs a signal from outside the data path, and as of 2026-08-10 the board carries three (firmware/src/stall_probe.hpp, core_idle.*): per-core idle across exactly the window that greyed the panel, the shape of the recovery that ended it, and the rssi at the time. Idle is measured from inside each core's own idle task — FreeRTOS run-time stats are compiled out of the precompiled Arduino framework, the fourth capability this vintage has decided here — by differencing the core's cycle counter across passes through an idle hook that returns false, which is what keeps the hook being called instead of the core sleeping.

The other failure, which deliberately does nothing

06 How any of this is proved

#6 no merge without replay coverage #7 allocation-free, measured

The harness is not test scaffolding around the engine; it is the host stand-in for the M3 firmware feed task, and it is deliberately the only place the engine is wired together. That is why the goldens and the console ladder can never disagree about what a trace means — there is one assembly, and both read it.

One detail carries more weight than its size suggests. TraceReader hands the adapter a string_view sliced out of the capture line by a string-aware scanner, not a re-serialised object. The adapter sees exactly the bytes the server sent, key order and spacing included — otherwise the harness would be validating a parser against its own output.

Since M4 stage A that reader knows there is more than one venue, and the split it makes is the load-bearing part. TraceReader owns the envelope — a line is a JSON object with an integer rx_ns, an object frame, and a clock that never goes backwards — and nothing else. Which fields the metadata must carry, whether a frame has a type at all, what a record's kind is called and how long the venue may legitimately be silent are all dialect, and dialect lives in venue.hpp's table and in a per-venue decoder. Three things that had been universal only because Anvil was the only venue are now table columns: a required integer ticker, a required string type on every frame, and the 1000 ms disconnect threshold. An absent venue tag reads as anvil, which is what let the tag land without moving a byte of the four committed Anvil traces — proven by diffing twelve outputs from three programs across them, not asserted.

Kraken's decoder at stage A is a classifier, not an adapter: it reads every record, names its kind, counts it, and emits no FeedEvents — which is checked by a counter rather than claimed in a comment. The replay driver therefore refuses a non-Anvil trace outright, because feeding Kraken's JSON to the Anvil parser would produce a dead ladder over a 100% parse-error count, and that is the shape of failure invariant #5 exists to forbid arriving through the test rig. The shape stage B has to fill is pinned by static_asserts on the decoder and sink signatures — strain 3's decision, applied for the first time.

What the panel costs

The HUB75 framebuffer is the largest single allocation in the object and the only one that is not static: 32 rows × 64 px × depth × 2 B × buffers, so 65,536 bytes at eight-bit colour double buffered. It is internal DMA-capable RAM, never PSRAM — the library only places it in SPIRAM when SPIRAM_DMA_BUFFER is defined, which this build never defines — and it is therefore competing with Wi-Fi, lwIP and mbedTLS for exactly the same pool. That is why the depth is chosen at run time from a measurement taken after the station associates and before the WebSocket client starts, and why the panel is the half that degrades: a colour bit is cosmetic, a TLS handshake that cannot allocate is not. The board prints the decision, our prediction, the measured heap delta and the library's own figure at boot, so three independent numbers have to agree.

Everything the renderer itself needs is static and small, and measured under the target toolchain rather than estimated: LadderView is 536 bytes (the 62-entry sparkline ring plus the trade-flash state), the font is 205 of .rodata, and the two palettes are 72 between them — twelve Inks at three bytes each, twice. Stage D moved the firmware's static RAM by 788 bytes (136,456 → 137,244, 41.6% → 41.9%) and its flash by 22,856 (842,889 → 865,745, 12.9% → 13.2%), most of the flash being the driver. Paint cost is bounded by construction — 64 horizontal lines and a header line, independent of book depth — and the board reports the worst one it has seen against the 33,000 µs frame period on every statistics block.

The whole engine as instantiated for one symbol is 20,480 bytes — adapter, book and channel together — against 512 KB of internal SRAM on the S3, before the HUB75 framebuffer takes its share. M3 stage A moved that figure by 2,352 bytes when the channel took its third slot, which is 0.45% of internal SRAM for a hand-off with no data race in it; the alternatives that fit in two slots are discussed in §08. Publishing costs one 1,168-byte copy per event at the baseline trace's 13.6 events/s, which is about 16 KB/s of memcpy (summary frames emit no event, so the event rate sits below the 15.6 frames/s wire rate). Neither number is close to a constraint, which is the point of having measured them: the argument for the dense window at M4 has to be made on delta-venue correctness, not on this.

What the parser costs the target

RAM is the wrong axis for the streaming parser: it has none. Compiled with the PlatformIO xtensa GCC 8.4 at -Os -fno-exceptions -fno-rtti, the whole translation unit is 5,861 bytes of .text, 0 of .data, 0 of .bss — and no .init_array, so it has no global state and no static constructors to order. Its working state is one stack frame — a cursor, a few scalars and a 64-byte token scratch — writing into the adapter's existing AnvilFrame, so parsing an 8 KB book frame costs no storage that was not already counted in the table above.

Stack is the figure that actually matters on a FreeRTOS task, and it is bounded and input-independent. -fstack-usage reports every frame as static — no alloca, no VLA — with the largest at 272 bytes (parse_anvil_frame, which the optimiser inlines the whole top-level walk into, scratch buffer included). The call graph is acyclic because the value skipper is iterative, so the deepest chain is fixed at about 600 bytes: a frame nested 5,000 brackets deep costs exactly what a flat one does. That is the property that makes the 64-container cap a memory decision rather than a crash-avoidance one.

The more useful measurement is the undefined-symbol list of that object, because it is the invariants stated as link errors that did not happen: __ashldi3 __divdi3 __lshrdi3 __moddi3 __udivdi3 memcmp memset strlen. No _Znwm, so nothing allocates. No __cxa_* or _Unwind_*, so nothing throws. Nothing from ESP-IDF. The four *di3 helpers are 64-bit integer arithmetic — and one of them is worth watching: wire_qty_to_steps does an int64_t divide and modulo per level, so ~250 levels at 12 frames/s is ~3,000 software 64-bit divisions a second on the LX7. That is inherited from M1's shared scaling and is identical in both parsers, so it is not a stage B regression, but it is the first thing to look at if the feed task ever needs headroom. qty_step is 1 for every venue we consume.

What the framework costs, and the one line in it that must not move

The target build is espressif32@6.5.0 / Arduino-ESP32 2.0.14 / xtensa GCC 8.4 — a precompiled framework, which is why so much of §08 is archaeology performed with objdump. Since 2026-08-16 it is that framework with one archive rebuilt: liblwip.a, from the esp-idf v4.4.6 tag the package's own versions.txt names, on the same toolchain generation and from the package's own build sdkconfig, changing a single Kconfig value — CONFIG_LWIP_TCP_WND_DEFAULT 5,744 → 17,232 (12 × MSS 1436). It ships as a local package override on [env], so it is the framework every environment builds against rather than an arm one of them opts into. The swap was verified before it was flashed: 564 global symbols identical across 87 members, the only member size delta tcp.c.obj +4 B, and tcp_alloc's packed rcv_wnd/rcv_ann_wnd literal pair reading 0x4350,0x4350 where the stock archive reads 0x1670,0x1670. Provenance and the rebuild scripts live in C:\local\framework-arduinoespressif32-wnd17232\WND17232-README.md. Cost of promoting it out of an arm, stated: no firmware environment builds on a machine that does not have that package, and platformio.ini carries the two ways out.

HAZARD — CONFIG_LWIP_TCP_RECVMBOX_SIZE must stay at the stock 6 on this vintage, and that is a measurement rather than an oversight. Kconfig's own guidance is WND / MSS + 2, which for the widened window is 14. Applied, the board completes TCP connect and the TLS handshake and then never receives the HTTP 101. Four archives from one pipeline, flashed A/B, map it completely: 5744/6 healthy, 17232/6 healthy, 5744/14 connects then watchdog-greys within 25 s, 17232/14 never completes an upgrade. The mechanism is formally open — the constant reaches one xQueueCreate in netconn alloc, read from source, and no further explanation has been earned. The failure is silent in the worst way, because every layer below the upgrade reports success. Do not "fix" the mbox to match the window without a soak behind it.

08 Where this design is carrying load it has not been asked to bear

the section to argue with

Everything above describes code that works and is green. This section is the honest counterweight: twelve places where the current shape is either unenforced, speculative, or about to be tested by a milestone that does not exist yet. Each is stated with what would break it and what resolves it.

0 · engine/ is proven host-buildable, and now target-buildable too

This entry used to be implicit and unenforced. The generated per-header check proved engine/ compiles on the host; nothing proved it compiles for the ESP32-S3, and the two genuinely disagree — the target toolchain that espressif32 6.5.0 pins is xtensa GCC 8.4, which does not accept -std=c++20 at all and whose libstdc++ lacks <span>, <ranges>, <concepts>, <bit>, floating-point from_chars, and constexpr algorithms. A header can be valid on the desk and reject on the board, silently, until M3 tries to link.

dc_engine_target_check now compiles the same generated TUs with the PlatformIO xtensa compiler when it is installed, at ESP-IDF-shaped flags. All eight engine headers pass; the hot path costs 1541 B of .text at -Os. The remaining strain is that the check is optional — a contributor without PlatformIO gets a host-only guarantee and a STATUS line saying so.

Resolves: CI that has the toolchain installed, so the target half is never the skipped half

1 · LevelSpan is a lifetime contract with no compiler behind it

The rule — copy before you defer — is enforced today only by the fact that a single consumer exists and it copies immediately. Nothing stops an M3 feed task from pushing a FeedEvent onto a queue, and if it does there is no diagnostic, no sanitiser hit on the common path, and a ladder that is subtly wrong rather than obviously broken. Invariant #7 forbids the obvious fix, since a guard type would stop FeedEvent being trivially copyable.

Resolves: a debug-build generation counter on AnvilFrame, asserted in LevelSpan — no release cost, no layout change

2 · SnapshotChannel was a claim; M3 stage A made it a mechanism

Until stage A this was a single slot behind two plain uint32_ts, with the header saying plainly that concurrent use was undefined and the M1 test exercising it single-threaded only. It is now three DisplaySnapshot slots and one atomic word: publish and consume each swap their slot into that word with a single exchange, so the writer's slot, the reader's slot and the ready slot are always three distinct objects and neither thread ever touches the frame the other is using.

Three rather than the two the constitution's wording implies, and that is the part worth arguing with. A seqlock and a two-slot buffer both let the reader copy a slot the writer is writing and then discard the result — the tear happens; the version check only stops it being drawn. Measured both ways: a seqlock of exactly that shape delivered 4.8 M frames with zero tears reaching the consumer on x86 GCC 10 -O2, and ThreadSanitizer flagged it on the first frame. So the case against it is not that it misbehaves on today's compiler; it is that the copy is a data race, and the only way to have both a seqlock and a clean report is a suppression sitting on the one cross-core path, on a target compiler generation nobody here controls. The third slot costs 2,352 bytes (§07).

Evidence: harness/tests/test_snapshot_channel.cpp races two threads over 100,000 frames whose every field is stamped from the frame's own version, so a delivered frame is either whole or provably spliced and the checker names the field where it split; harness/tests/tsan_clean.txt is the committed ThreadSanitizer report. Both mutation-verified — collapsing the slots back to M1's one fails at version 12.

Resolves: done — the residual strain is that TSan needs Linux, so the report is refreshed by hand via harness/tsan.sh rather than by the host gate

3 · There is no VenueAdapter type — decided at M4 stage 0, first applied at stage A

The architecture diagram names one; the code has AnvilAdapter with a template Sink, no base class and no concept. That is the right call for invariant #7 — no virtual dispatch on the feed path — but it means "what an adapter is" is currently convention. Kraken at M4 is the forcing function: either a C++20 concept pins the shape, or two adapters drift apart with nothing to catch it. This is the largest open design question in the repo.

Updated 2026-08-16 (M4 stage 0): the toolchain half is settled, by compiling rather than arguing — and the expected blocker is not there. Four candidate spellings were put through the exact command dc_engine_target_check runs (CMakeLists.txt:97-101), on xtensa-esp32s3-elf-g++ 8.4.0 with host g++ 15.2.0 for contrast. #include <concepts> is a fatal error — the header does not exist. The C++20 concept keyword alone is error: 'concept' does not name a type … note: only available with -fconcepts — and compiles cleanly with that one flag added. Measured cost of the flag on the engine as it stands: 9/9 headers and the streaming parser compile, and the object file is byte-identical (same hash, .text 5,861 B either way). So option (i) does not drag in the GCC 15.2 / pioarduino move, and is not milestone weight.

Three conditions ride with it. The <concepts> library is absent, so any concept must be hand-written from requires-expressions plus <type_traits>. Only the C++20 spelling is portable — GCC 8.4 also accepts the Concepts-TS concept bool, which GCC 15.2 rejects outright (error: variable concepts are no longer supported), so the target's most natural spelling would break invariant #1's host half. And GCC 8.4's -fconcepts is the Concepts TS, not C++20 concepts: the syntax overlaps, the semantics need not, and nothing has measured that. The residual risk is therefore a concept that means one thing on the desk and another on the board — the exact failure class invariant #1's target half exists to catch, arriving through the feature meant to make the boundary safer.

Updated 2026-08-17 (M4 stage A): option (ii) is implemented, in the harness, and the thing it pins is not the one this card predicted. The second adapter does not exist yet — Kraken's stage-A decoder is a classifier that emits no FeedEvents — but the second decoder does, and it is the first thing that ever had to fit the shape. trace_decoder.hpp carries SinkContract<Sink> (invocable with const FeedEvent&, returning void) and DecoderContract<Decoder> (a kVenue tag, classify, decode, on_transport_gap), both instantiated so a third venue fails the build here rather than diverging quietly. The sink contract is instantiated inside each decode(), so it fires on the sink type the caller actually passed — the one thing option (ii) still buys at the call site. noexcept is deliberately not asserted, though the stage-0 write-up floated it: the only real sink in the tree pushes onto a std::vector and calls a std::function, so asserting it would either reject the live path or turn a throw into std::terminate on the desk. Option (ii)'s stated weakness showed up exactly as predicted and is worth recording as confirmed rather than anticipated: a contract violation cannot be unit-tested, because a failing static_assert is a compile error and breaks the build that would run the test. test_trace_venue.cpp checks the underlying detection traits instead, which is the nearest reachable thing.

Resolves: DECIDED 2026-08-16 (M4 stage 0) — option (ii), static_asserts on the sink signature. Not yet implemented; that is M4's, with the second adapter in front of it. The toolchain question is closed and its answer did not choose the design: a C++20 concept costs one flag and a byte-identical object file, not a framework migration. (ii) wins because the flag's cheapness is the trap. The hazard was never "it will not compile" — it is that both would compile and mean different things: the host builds C++20 concepts, the target builds Concepts TS behind -fconcepts, and engine/ acquires two dialects with one spelling. That is a worse failure than convention because it type-checks, and the property that would quietly stop being true is invariant #1's "the same translation units build on host and target". Option (i) re-opens if the toolchain moves for unrelated reasons, or earlier if someone runs the one missing experiment — a concept whose subsumption behaviour is exercised on both compilers and shown to agree. Decision: ARCHITECTURE.md §9 (2026-08-16 stage 0) and docs/briefs/M4-stage-0-price-the-kraken-wire.md

21 · Two hand-rolled JSON scanners, sharing a grammar and not a line of code — incurred at M4 stage B1

anvil_frame_streaming.cpp (984 lines) and kraken_frame_streaming.cpp (~600) are both allocation-free recursive-descent-free scanners over the same subset of JSON. They share whitespace handling, string scanning with \u escapes, number-token slicing, and an iterative skip_value over a bit-packed container stack. None of it is shared code.

The extraction was considered and refused, and the reason is specific rather than schedule pressure. Anvil's scanner is deliberately bug-compatible with nlohmann 3.11.3, because its contract is that the reference implementation's observable behaviour — accidents included — is the specification (anvil_frame.hpp). Its number scanner treats an integer too large for uint64 as a float so the frame becomes a shape error; its skip budget is 64 containers per skipped value; it has a measured escape divergence at 64 bytes. Kraken has no reference to be equivalent to and wants none of those. A shared header would have to carry one venue's accidents into the other, or grow a flag per quirk — which is worse than the duplication, because it would make the quirks look like options.

What makes this a strain rather than a decision: the duplication is real, it is ~400 lines, and the failure mode is that a bug fixed in one scanner is not fixed in the other. What bounds it: neither scanner is shared, so neither can break the other, and both are pinned by goldens over committed traces. The trigger to extract is a THIRD venue — Binance at M5 — because three instances distinguish the general primitives from two venues' accidents, and two do not.

Resolves: M5, if Binance needs a third scanner — and the extraction is then a refactor with two golden suites already holding it still

23 · Host and target compute the book’s age by different code — latent since M4 stage A2; owner, expiry and tripwire assigned at B1; RENUMBERED FROM 22 AT B2

This card was opened as “22” at stage B1 and there was already a card 22 — One reader, two venues, opened at stage A and carrying six inbound references from the stage-A briefs. Two live cards under one number in a document whose whole job is to be cited is a defect in the citation, so this one moves to 23 and the older number keeps its references. The three references that meant THIS card (M4-stage-B1-the-adapter.md and M4-triage-of-the-twelve.md) were corrected in the same edit; if you are reading a brief dated on or before 2026-08-18 that says “strain 22” and means the age divergence, it means this card.

harness/include/dc_harness/age_estimator.hpp is a sliding-window deficit against a baseline latched once per connection. firmware/src/staleness.hpp is a cumulative estimator against a hardcoded kSummaryPeriodUs = 500000. They answer the same question and they are not the same arithmetic — the harness one was written at A2 precisely because the firmware one cannot see a venue whose cadence it does not already know, and A2 superseded it in the §9 log without deleting it.

This divergence is invisible to every host test, and that is the whole problem. ctest exercises the harness estimator; the board runs the other one; no check anywhere compares them, because there is nothing to compare — they are different code reached by different callers. It cannot be closed by testing. It can only be closed by deletion, which is what stage B1’s Part B item 8 was for.

Status: LATENT, not active. Nothing on the target reads Kraken until D. The board today runs Anvil, where the firmware estimator’s hardcoded 500 ms happens to be the right constant — so the two agree by circumstance, which is the coincidence class one level up (ARCHITECTURE §9, 2026-08-18) and exactly why it is written down rather than left to the next reader to notice.

At that instant the firmware estimator is measuring a 1 Hz heartbeat against a constant that says 500 ms, so the age on the panel is wrong by a factor of two and nothing on the board says so. 4 · The book retains 8,552 bytes to publish 1,168

kBookCapacity is defined as kMaxSnapshotLevels — 256 per side — while the panel renders 27. The justification is the M7 zoom mode, which is four milestones away and may never take that form. The coupling itself is defensible (a snapshot the adapter accepted can never be truncated a second time), but the value is speculative capacity.

Resolves: cheap to leave; revisit only if S3 SRAM gets tight against the framebuffer

5 · Book's face has never met a delta

M4 requires the tick-indexed dense window to land "behind this same apply()/publish() face". That is an untested assumption. Re-anchoring by bounded copy, a cold tail in a map, and CRC verification are all things a snapshot-only book never had to express, and if the face does not survive them, this section of the design is what changes.

Resolves: M4 — and a face change there is a §9 amendment, not a refactor

6 · Every event republishes the whole ladder

publish() bumps version_ unconditionally, so a trade-only event produces a new version and the render side redraws even though no level moved. At Anvil's ~15 events/s that is comfortably under the 30 fps target and costs nothing worth reclaiming. It becomes a real question only at a venue with a much higher per-event rate.

Resolves: nothing to do now; note it before M5's Binance diff stream

7 · format_px returns a std::string — closed at stage D

The console ladder allocates freely, which is correct for the display edge on a desk. But format_px lives in the harness header a firmware renderer will be tempted to imitate, and the target must use format_scaled into a stack buffer instead. Nothing enforced the distinction, and the alloc probe covered the feed path and stopped at the channel.

Closed 2026-08-10. The firmware renderer does use format_scaled into a fixed stack buffer, and that is now an assertion rather than a habit: test_ladder_render.cpp runs 200 frames of LadderView::draw — every depth, both statuses, a trade print every frame — inside the alloc probe's window and requires the counter not to move. The probe replaces global operator new, so a std::string, a container or a heap snprintf anywhere under the renderer moves it.

And the assertion carries a positive control, which it needed. Two hand-written mutants of draw() — a new int and a std::string(64,'x') — were silently deleted by GCC's allocation DCE and "passed" the test while visibly executing (a side effect in the same block failed a different case, which is how they were caught). Only an allocation whose pointer escapes through a volatile store survives the optimiser and moves the counter, by 200 exactly. The control is committed beside the assertion, because an allocation counter that is not wired reports zero for every possible renderer.

The same review pass turned up the render side's one real arithmetic defect, and a property test found it rather than a reader: bar_length was the obvious 64 * qty / max_qty in int64, which is undefined behaviour once qty passes INT64_MAX / 64. No venue we consume quotes anything near it, but Qty is the full 64-bit type by deliberate design (§02) and the adapter's only quantity guard is raw < 0. Both operands are now shifted down together until the product is safe. The example-based cases all used quantities a human would think to write down; the 3,000-step random walk did not.

Resolved: M3 stage D — the render path is inside the probe, and the probe has a control

8 · The harness reads meaning into Seq == 0

StaleEpisode::gap_seq == 0 is used as "not yet set", which is only safe because AnvilAdapter::next_seq_ starts at 1 and 0 is reserved for "no event yet". That is a real convention, documented in the adapter — but it is an engine convention that harness logic now depends on, across a boundary neither file names.

Resolves: a one-line comment, or an explicit optional; low stakes, worth knowing

9 · Two parsers now have to stay the same thing

M3 stage B closed the last allocating hole on the feed path — the parser is now allocation-free, measured over both traces with global operator new counted, and it compiles for xtensa GCC 8.4 with no undefined symbol implying a heap, an exception or ESP-IDF. That part is settled. What it bought in exchange is a new obligation: one declaration with two definitions is two chances to be right.

The reference is not a spec written down anywhere; it is nlohmann 3.11.3's behaviour, including the parts Anvil never exercises. Duplicate keys resolve last-wins because that is what a std::map filled through operator[] does. An integer too large for uint64_t is a float, so a quantity of 99999999999999999999 is a shape error rather than a saturated number. A NUL byte ends the document even mid-buffer. None of that is written in anvil_frame.hpp, and all of it is load-bearing, because the adapter files the three failure statuses into three different counters and the counters are goldens.

The mitigation is that the equivalence is executed, not reviewed: test_parser_equivalence.cpp is compiled into both binaries and holds both implementations to one table, covering escapes, surrogate pairs, over-range integers, invalid UTF-8, error precedence under reordered keys, and duplicate keys at every level. Three divergences remain, deliberately, and are asserted on both sides of their boundary in test_streaming_parser.cpp — a one-sided test would still pass if the limit silently fell — so that a later session cannot quietly close one, or shrink one, without reading why it was opened. They are: a single skipped value may nest 64 containers and not 65 (the container stack is one uint64_t, which is what keeps the skipper iterative and heap-free); an escaped price whose unescaped form reaches 65 bytes is BadPrice rather than its value; and the open band between DBL_MAX and 1e309 is treated as finite.

How much that mitigation is worth was measured rather than assumed. Three independent agents ran roughly 2.4 million differential inputs through both implementations — byte-mutated real frames, exhaustive truncation at every offset, all 65,536 \uXXXX escapes, all 65,536 two-byte raw sequences, every permutation of the top-level member set, integer and double boundary sweeps — and found no disagreement outside those three. The sharpest evidence is a corpus built so that none of the three can fire (nesting capped at 20, no literal near 1e308, every escaped string under 40 bytes) replayed across 24 SymbolSpec configurations: 567,842 records, zero differences.

Resolves: never fully — it is the standing cost of the seam. Keep the equivalence table growing with every wire surprise; if the two ever have to diverge on something Anvil can actually send, that is a §9 amendment, not a patch

10 · There are now two definitions of "the feed has stopped"

The host replay driver greys on a hole between frames; the M3 stage C firmware greys on a hole between events reaching the book (§05). Both use 1000 ms, and on every captured input either has ever seen they agree exactly — 640 ms at M0, 391 ms on the 2026-08 re-measurement, identical under all three counting rules both times. They differ where a trace file cannot go: bytes that arrive and decode to nothing.

The 2026-08 work found the first input on which they do separate, and it is not a malformed frame — it is a slow client. Against a socket throttled to the board's message rate the worst silence is 141 ms counted by frame arrival and 594 ms counted by book event, because Anvil sheds coalesced book frames to a backed-up consumer while the 2 Hz summary broadcast keeps arriving. So the weaker rule is not merely less strict in theory; on a real stream to a real device it under-reports the thing the panel is actually showing by 4×. That strengthens the case for one rule, and it means the alignment is no longer golden-neutral by inspection — the M4 session has to measure it on the throttled trace, not only on the two committed ones.

The firmware's rule is the better one — it is the version that cannot leave a frozen ladder reading Live — but having two is a real cost, because the goldens now pin the weaker rule and the panel runs the stronger one, so the harness can no longer be said to preview the firmware exactly. The right end state is one rule in both places.

Resolves: M4 — move the host driver onto the event-armed rule. Golden-neutral on all three committed traces (the worst gap is identical whichever way it is counted: 640.2 ms at M0, 391 ms in 2026-08), but no longer neutral in general — a throttled stream separates the two rules 4× — so the M4 brief owns a throttled trace as well as a re-pin, and it is a change to golden-covered code that belongs in a brief, not in a firmware stage

11 · Invariant #7 is now two claims, because the transport is not ours — the per-event churn closed 2026-08-16; the measurement gap did not

The original card, kept because the reasoning is what makes the closure legible. Every earlier statement of "allocation-free steady state" was about code in this repo, and could be proven absolutely: alloc_probe counts zero over both traces, and the streaming parser's xtensa object has no undefined operator new to call. Stage C was the first time the invariant met a library nobody here wrote, and it lost. esp_websocket_client dispatched every event through esp_event_post_to, which heap-copied the 28-byte payload and freed it when the handler returned — about 37 balanced calloc/free pairs a second at three DATA events per book frame.

That path is gone with the library. The owned client reads into a 4 KiB buffer that lives in the object's BSS and drives WsFrameParser → FrameReassembler → FramePipe with no event loop, no dispatch hop and no per-message block: there is no esp_event_post_to anywhere in the RX path any more, so the 37 pairs a second are not merely bounded, they do not happen. The strict reading of invariant #7 reaches one hop further out than it could at stage C.

What does not close is the part that was never about the websocket client. esp-tls still allocates per handshake — inside the boundary the invariant already names ("after connect and first snapshot") — and ESP-IDF heap tracing is still compiled out of the precompiled framework, so heap_probe still detects a leak or fragmentation rather than proving the absence of churn. The 23.6 h soak is the evidence that stands in for the proof: free ended +452 B against its own baseline after 331,682 frames, with the largest free block unmoved.

Resolves: the transport half of the split is closed by deleting the library that caused it (2026-08-16). The residual is the measurement, not the behaviour: heap_trace_start is still unavailable on this framework, so the claim is supported by a day of flat sampling rather than by a counter. That resolves only on the platform decision — pioarduino / IDF 5.x — and is no longer urgent enough to drive one

12 · Something stalls the board's feed for seconds, and only the panel can see it — closed 2026-08-10, it was the Wi-Fi link

The desk half of this project is measured to death and the board half is measured by three counters and a serial line. That asymmetry has now produced its first real defect: on the bench the panel greys every 15–20 s with the socket up (wd_gaps=5 in 90 s, sock_gaps=0, connects=1), worst silence 2,461 ms — and nothing at the desk end of the same LAN reproduces it. Anvil runs at 17.02 frames/s with a 391 ms worst gap; a socket deliberately throttled to the board's own 8.30 msg/s still has a worst book-event silence of 594 ms and trips the watchdog zero times in four minutes. Whatever costs the board those seconds happens on the board.

It very nearly became an architectural change instead of a bug. The obvious reading of "the board sees ~6 msg/s where M0 saw 15.5" is that the venue slowed, and the fix for that is to raise kRxWatchdogMs — which would have suppressed the symptom, moved a committed golden, weakened the invariant-5 proof, and left a 2.5 s freeze of the feed pipeline in place, reading Live. What stopped it was measuring the premise before acting on it. The general form is worth keeping: a threshold that fires is evidence about the thing it watches, not about itself, and the constant is the last place to look.

The instrumentation was the real gap, and it is now closed. worst_gap is a single high-water mark with no distribution behind it, so the board could report that it saw 2,461 ms but not how often, nor whether the hole was in arrival or in decode, nor whether the feed task was starved or the socket was quiet. Every question the desk answers in one command was unanswerable on the device that has the problem. As of 2026-08-09 the board carries the arrival and event gap histograms, the arrival→event latency and the queue-wait split described in §05 — 128 bytes of static storage, allocation-free, and the bucketing host-tested. The measurement itself is still owed: it takes a ≥10-minute bench run with no deliberate disconnects, which is the owner's, and until then this strain point is instrumented but not diagnosed.

One candidate was narrowed without the board, and it is the one the characterisation brief expected to be cheapest: Wi-Fi modem sleep. Arduino-ESP32 2.0.14 does default it on for the S3 (_sleepEnabled = WIFI_PS_MIN_MODEM), but this firmware has called WiFi.setSleep(false) since the stage C draft, and after WiFi.mode(), which the shipped source says is the order that makes it take effect. So the experiment was not "does turning it off help" — it was whether turning it off was ever taking effect, and whether turning it back on reproduces the stall. It does not reproduce it and it does not remove it: 17 holes in 11 minutes with power save off, 25 in 10.5 minutes with it on, worst 2,461 ms and 1,893 ms respectively. Modem sleep is not the mechanism.

The bench ran, and the split the instrument was built around could not decide it. Both runs held connects=1 and sock_gaps=0 while arrive and event filled their >1 s buckets together — which the 2026-08-09 verdict table reads as "transport", and which is an over-claim on two counts, both now written into §05. The arrival stamp is taken inside esp_websocket_client's task, downstream of the Wi-Fi driver, lwIP and the TLS decrypt, so an arrival-side hole does not exclude a busy Core 0; and Anvil's per-socket coalescing sheds to a slow consumer, so "the server stopped sending" and "the board stopped keeping up" are the same observation seen from two ends. The two candidates are entangled by construction, and no amount of instrumenting the data path separates them.

15 · The panel's double buffer is safe by cadence, not by handshake

Double buffering is what keeps a book that redraws thirteen times a second off the panel mid-write. The contract it rests on is that the buffer being drawn into is not the buffer being scanned — and on the ESP32-S3 the library does not enforce that. Bus_Parallel16::flip_dma_output_buffer() re-points the tail of the DMA descriptor chain and returns; the wait for the previous buffer to drain is present in the source and commented out (gdma_lcd_parallel16.cpp:444). So the flip is asynchronous, and nothing stops the render task writing into a buffer the DMA has not finished with.

What actually makes it safe is arithmetic that lives in two different files and is stated in neither: the panel scans at roughly 100 Hz, and the render task redraws at most once per 33 ms period and typically once per published version. One scan is comfortably inside one period, so the DMA has moved onto the presented buffer long before the next paint begins.

And the number that margin was computed from was wrong, in the safe direction, by luck. The 2026-08-11 bench found that the S3 backend buckets i2sspeed rather than using it — anything at or below 10 MHz lands on divider 16, i.e. 160/16 = 10 MHz — while the library's refresh loop still computes from the 8 MHz it was asked for. So every refresh=105 Hz this firmware printed before that date is ~25% low and the panel was really scanning at ~131 Hz. The board had been reporting both halves on adjacent lines (Clock divider is 16) since the first boot.

Both figures are now printed explicitly at boot, and test_panel_budget.cpp pins the refresh at every divider worth considering — 16 → 131 Hz, 24 → 87, 32 → 65, 40 → 52 — with the assertion that a scan must still fit inside one render period. So the margin is checked rather than assumed, which is the half of this strain point that is now closed. What remains open is the flip itself: it is still asynchronous, and safety still rests on cadence rather than on a handshake.

The failure mode if either moves is the quiet kind. Raising the draw rate toward the 30 fps the frame period allows, lowering min_refresh_rate, or dropping to a colour depth whose scan is slower narrows the margin, and what comes back is tearing — which reads as a flicker somebody blames on the ribbon cable rather than as a contract violation. The colour-depth ladder makes this reachable without a code change: a board that only fits depth 4 gets a different refresh rate than the one this was reasoned about at.

Resolves: half closed 2026-08-11 — the refresh rate is now measured rather than assumed, printed at boot as nominal-vs-actual, and asserted against the render period at every divider. The flip remains asynchronous, so the remaining work is a boot-time guard that logs loudly if a scan ever stops fitting inside one period, and that only becomes necessary if the draw rate is raised or the clock slowed further

Everything else in this document treats the two halves as meeting at SnapshotChannel and nowhere else — one writer, one reader, one meeting point, and §02's whole argument rests on it. The 2026-08-11 bench found a channel the architecture does not model at all, and cannot: the panel's switching couples into the Wi-Fi radio.

cfg.clkphase = false clears a ghosting artifact beside the header glyphs completely, and collapses inbound traffic from ~6 msg/s to ~2 msg/s against Anvil's 17/s — reproduced consistently in both directions, with sock_gaps=0, connects=1, 0 % lost and both cores ~96 % idle. The feed is not slow; the data is not arriving.

It cannot be software, and that is what makes the mechanism readable. clkphase reaches exactly one thing — esp_rom_gpio_connect_out_signal(CLK, LCD_PCLK_IDX, invert, false), a GPIO-matrix inversion on one pin — with no change to the DMA descriptors, the data rate, the memory bandwidth or any CPU work. Inverting CLK only moves when its edge falls relative to the thirteen data and control lines beside it. At the default they are staggered; inverted, they transition together, and ~14 outputs switching simultaneously down a bare-jumper ribbon with no ground plane is a far larger di/dt on a shared return, a hand's width from the DevKit's 2.4 GHz antenna. The panel samples its own data better and jams its own radio.

The same evening produced the corollary from the other direction: the ghosting tracks the switching activity of the paired scan rows rather than their current, so dimming the bars made it worse — under BCM a channel at 255 is DC-on for the whole frame while an intermediate value toggles bit-planes several times per frame. The aggressor is edges, not amps, in both directions.

Resolves: not in firmware. clkphase stays at the library default because the feed wins — a ghosted header is cosmetic, a 2 msg/s feed greys the panel every few seconds. S3_LCD_DIV_NUM=24 ships as a partial mitigation (a third off the edge rate) and helped one of the two header fields. The rest is M6: this turns the carrier board's ground plane, short leads and 2× 74HCT245 buffers from tidiness into requirements, and clkphase = false should be re-tested there — on a proper interconnect the noise argument may simply evaporate and the ghosting fix becomes free. Full record in hardware/BRINGUP.md. Still owed: CLK on a 10× probe, since M2's survey used 1× and recorded "edge softening partly attributable to the probe" — the edge rate both symptoms turn on has never been characterised

17 · Invariant #5 protects against stopped and against wrong. It has no concept of old

This is the strain point with the largest gap between what the document claims and what the object does, and it was invisible for three stages because every instrument in this design measures the same family of failure. The RX watchdog and the gap histograms measure stopped. The parse counters and the reject log measure wrong. The stall probe measures whose fault the stopping was. A feed that is running perfectly, parsing perfectly, and showing a book a hundred seconds behind the market fails none of them.

Measured on 2026-08-11, single connection, parse=0 cont=0 trunc=0 oversize=0 qfull=0 abandoned=0, no_slot=2 of 1,703, both cores 85–92 % idle, a→e worst=20 ms: the web client was frozen at 12:05:02 and the panel reached the same state at 12:06:38.7. 96–98 seconds of age, with every counter green. Two symptoms that had read as separate bugs are this one — the "frozen bid" (10.0034 x67 across 502 published versions) was the board faithfully replaying a real stretch of history, and the "5 Hz refresh" was summary at 0.82/s of 2.00/s beside book at 5.60/s of 13.44/s: two independent counters, the same 41 %.

The mechanism is now measured rather than argued. tools/anvil_freshness_probe.py runs two sockets from one process — one drained flat out as a reference, one sleeping 250 ms per message — and matches Anvil's global wire seq across both, so staleness is a subtraction against a real clock instead of an inference from a rate. Over 150 s: every frame kind thinned to the same fraction (book 25.5 %, summary 25.7 %), lag rising linearly to 111 s with no plateau, at +0.745 s per second by seq-matching and +0.745 s/s predicted independently from the drain fraction. Anvil queues; it does not shed — which withdraws the 2026-08-09 finding in ARCHITECTURE §9 and, with it, the sentence in strain 12's verdict table that reads "Anvil shed the middle because this socket backed up". The implied per-socket queue was ~12.4 MB and still growing.

The instrument that closes half of it is firmware/src/staleness.hpp: summary is a fixed 2 Hz timer broadcast, so the deficit between 2.00/s and what this socket receives, integrated since connect, is the age — free, from a counter the adapter already keeps. ESP-IDF-free and host-tested, reset per connection, printed as -- age beneath -- rate. It raises no Gap and nothing branches on it, deliberately: making the panel act on age is a vocabulary change and therefore stop-and-raise.

And the reason it cannot simply become a sixth GapReason is structural, which is what makes this a design strain rather than a to-do. Invariant #5's rule is only a Snapshot clears stale, which is exactly right for absence of data — every existing reason is "something is missing". Age is the presence of old data, and under queuing the board is adopting stale Snapshots at 5.6/s, so a Gap{TooOld} would be cleared ~180 ms later by the next stale frame. The panel would flicker, not grey. Fixing that means the clear condition becomes "a Snapshot that is fresh", which puts a wall clock inside a book that is deliberately clock-free and replay-driven.

Decided and landed at M4 stage A2 (2026-08-17): the §5 route, and invariant #5 is NOT extended. DisplaySnapshot carries age_ms and has_age — both in padding the hand-off already had, so the 1,168 B is unmoved and now pinned — the console header renders it to minutes and hours, and nothing branches on it. That last clause is what the paragraph above argues for and it survived contact: age stays a number, grey stays the liveness clock's, and the flicker problem never arises because no clear condition had to be redefined. What did change is how the number is computed. Stage E integrated a deficit from a hardcoded 2 Hz since connect; A2 replaces that with the supremum of the deficit over a sliding 256-arrival window, taken against a baseline the connection measures for itself in its first window and then freezes — because a fresh socket's server-side queue is empty, and that is the only moment a single client can measure the venue's clock. The rolling median the grey threshold uses cannot serve here: an age computed against it reads 0.0 s through a 111 s backlog.

Two residues, both named rather than closed. (1) firmware/src/ staleness.hpp still runs the stage-E cumulative estimator with kSummaryPeriodUs = 500000 in it, so until stage B lifts age_estimator.hpp across, the host and the target compute the book's age two different ways — a divergence that is invisible in any host test by construction, which is exactly why it is written here. (2) The estimator has a proved blind spot: a socket already behind when it latched cannot detect it, because "the venue broadcasts at 2 Hz and I am two minutes behind" and "the venue broadcasts at 0.5 Hz and I am current" are byte-identical on the wire. On the one real backlogged capture it reads 12.5 s against a true ~122 s. That is the case the client ping closes, deferred to M6 with its reason recorded.

A third residue existed and was closed at M4 stage B2 (2026-08-18), and it was the load-bearing one. Every word above assumes the venue QUEUES — the deficit is read as a lag, and if the venue SHED instead, the identical deficit would appear with no lag behind it at all. At Anvil that premise is measured and readable in source. At Kraken it was neither, and B1 pinned it as a test that asserted an assumption and named B2 as its owner rather than letting it become a caveat carried to M5. B2 measured it: Kraken queues. One connection, 80 s, a socket throttled with the 120 ms drain lever, and three signals that fail under opposite hypotheses — 331/331 checksums clean (nothing lost), lag growing +0.690 s/s to 26.0 s off the venue's own microsecond timestamp (everything late), and on release a backlog draining at 64.2 msg/s against a 19.5 msg/s baseline (there was a backlog). age_ms at Kraken is a lag and stands as shipped. What the measurement does NOT say is stated with it: the lever is TCP backpressure, so it describes the whole path rather than Kraken's send queue, and unlike Anvil's it is an observation and not a contract — tools/kraken_backpressure_probe.py re-runs it in one command.

Resolves: the measurement landed at stage E1, the rendering and the §5 decision at M4 stage A2 — age_ms is on DisplaySnapshot, invariant #5 is untouched, and the panel can finally say live, and ninety seconds behind. Still open, and both now have owners: stage B lifts the estimator into firmware/ and deletes the cumulative one (until then host and target disagree by construction), and M6 owes the client ping, which is the only instrument that can see a socket that was behind from birth. Briefs: docs/briefs/M3-stage-E-the-age-of-the-book.md (the proposal), docs/briefs/M4-stage-A2-the-age-meter.md (what shipped); desk evidence in hardware/bench-2026-08-11-feed-lag.md

22 · One reader, two venues — and the pressure is on the traces, not on the reader

Opened 2026-08-17 (M4 stage A). TraceReader now validates an envelope and hands the dialect to a per-venue decoder, with the metadata's venue tag selecting a row in venue.hpp. That is the right shape and it landed cleanly: the four committed Anvil traces are byte-identical through the changed readers, and dc_replay reads all four Kraken slices end to end (six as of B2, which added the mid-stream and resync captures). The strain is not in what was built; it is in what the arrangement now makes cheap.

Three specific loads it is carrying, in the order they will be felt.

The venue table is a second copy of numbers the firmware also holds. venue_traits(Anvil).stale_gap_ms is 1000 and so is kRxWatchdogMs, in a different file, in a different build, with nothing that can tell if they diverge. Stage A was instructed not to touch the firmware constant and did not; stage B lifts this table into the shared one and the divergence window closes then. Until it does, a session that re-derives one number must be told to go and look for the other — which is a rule someone has to keep rather than a property the build enforces, and this repository's answer to that shape of problem is normally to make it structural (ARCHITECTURE §9, 2026-08-10: the renderer cannot name a colour, because a rule that has to be remembered fails the first time someone adds a widget). Nothing structural is available across a CMake build and a PlatformIO one until they share the table.

Adding a venue is now four edits in two languages, and only three of them fail loudly. A row in kVenueTable, a decoder satisfying DecoderContract, a taxonomy pin, and a row in tools/tracefile.py's VENUES. The first three are compile-time or ctest failures. The fourth is not: a Python tool would simply refuse a trace the C++ reader accepts, which reads as a bad file rather than as a missing row. M5 is the test of whether that asymmetry matters.

And the one with teeth: the replay driver can now be pointed at a trace it must not decode. Today it refuses loudly, because there is exactly one adapter and anything else is an error. When stage B adds the second, "which adapter decodes this trace" stops being a check and becomes a dispatch — and a dispatch that picks wrong produces a golden derived from the wrong parser rather than an exception. The mitigation that exists is that the venue is read from the file rather than passed in by the caller, so a trace cannot be decoded as the wrong venue by a mistake at the call site. The mitigation that does not exist yet is anything checking that a Kraken golden was produced by the Kraken adapter, and stage B should not ship without one.

Stated as a closing condition rather than as a worry, because the difference is what makes it checkable (added 2026-08-17 at the owner's review): "A Kraken golden fails if it was produced by the Anvil parser. The decoder's identity travels with the pinned output, and a mutation test that swaps the dispatch expects red." Note what that asks for beyond a passing test — the identity has to be in the pinned artefact, not merely known to the harness at run time, because the failure being guarded against is a golden that looks right. And note the shape it shares with every other pin in this repository: it is only worth anything if the mutation has been run, which is why the sentence names the mutation and not the assertion.

Updated 2026-08-17 by the staleness ruling, and the first clause is now HALF CLOSED in an unexpected direction. The venue table no longer duplicates kRxWatchdogMs, because it no longer holds a duration at all: the double stale_gap_ms became a string_view liveness_signal carrying the signal's name, and the threshold is derived at runtime from that signal's own rolling median (liveness_clock.hpp). There are now no two numbers to drift. What remains of the clause is smaller and different: the firmware still holds a constant the harness no longer has, so stage B's job is not to reconcile two numbers but to delete one.

And the third clause gains a sibling that is the same shape. A dispatch that picks the wrong adapter produces a golden derived from the wrong parser; a liveness signal named wrong produces a panel that greys on the wrong evidence — and both fail by being plausible. The Python and C++ tables must agree on what summary and heartbeat mean (tracefile.is_liveness mirrors venue.hpp), and nothing checks that they do: the four-edits-in-two-languages count from the second clause is now five, and the new one is in the silent column with the rest.

Resolves: partly at stage B (the venue table merges with the firmware's; the second adapter turns the driver's refusal into a dispatch and owes a check that the dispatch was right), partly at M5 (whether the Python/C++ table split costs anything real), and partly never — two venues means two of some things, and the card exists to keep the count visible rather than to drive it to zero
